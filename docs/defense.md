# Защита: короткие ответы на вопросы из задания

Шпаргалка к живому показу. Каждый ответ занимает 30–60 секунд и ведёт к файлу, который можно открыть на экране. Перед встречей пройдите [сценарий показа](demo-script.md) сами минимум один раз.

## 1. Покажите основной сценарий без записи

Запускаю START-DEMO.cmd и открываю http://localhost:3077.

1. «Создать смету» → ASUS X515, чистка 180 000 + кулер 220 000, объяснение, срок, гарантия → предпросмотр → сохранить → опубликовать.
2. Копирую ссылку, открываю её в приватном окне: клиент без регистрации задаёт вопрос «Кулер новый?».
3. В кабинете у сметы статус «Нужен ваш ответ» → отвечаю. В окне клиента согласую ремонт.
4. «Новая версия» → кулер 250 000 → публикую. Старая ссылка показывает, что условия заменены, и прежнее решение сохранено.

Если AI ответит 429, говорю: «Внешний бесплатный провайдер ограничил запросы, основной сценарий от AI не зависит» и пишу объяснение вручную.

## 2. Какую часть сделал я, а какую AI

Я выбрал нишу и проблему, сформулировал три сценария и ограничения MVP, ставил задачи AI-агентам, проверял результат в браузере и решал, что исправить. Код, тесты и большую часть документов написали coding-агенты (Codex, Claude Code) по моим задачам. Список инструментов приведён в [ai-usage.md](ai-usage.md).

Примеры, где проверка поймала ошибку AI:
- reasoning-модель тратила весь лимит токенов до JSON → поднял бюджет и отключил вывод рассуждений;
- после изменения заметки можно было перенести устаревший AI-ответ → теперь перенос блокируется;
- чистый CI нашёл миграцию, которая применялась не в том порядке → исправлено именем миграции;
- AI мог вернуть ID работы не из каталога мастерской → сервер такие ответы отклоняет.

## 3. Как проверял код, безопасность и данные

- **Тесты:** TypeScript и ESLint; 55 unit-тестов; 13 интеграционных на настоящей PostgreSQL; браузерные Playwright-сценарии на ширинах 390/768/1440. Всё это гоняет CI в GitHub Actions.
- **Изоляция:** каждый запрос фильтруется по `workshopId`. Тест проверяет, что чужая мастерская не может прочитать, изменить или опубликовать смету.
- **Деньги:** итог пересчитывает сервер, сумме из браузера он не доверяет.
- **Ссылки клиента:** случайный токен, в базе хранится только его хеш; публичный ответ содержит только явно разрешённые поля, внутренняя заметка в него не попадает.
- **Гонки:** публикация и решение блокируют строку сметы (`FOR UPDATE`), поэтому одновременные «согласовать» и «отказаться» дают одного победителя.
- **Инварианты в БД:** UNIQUE, CHECK и триггеры запрещают менять опубликованную версию даже прямым SQL.
- **Секреты:** только в `.env`, файл исключён из Git; платные AI-модели заблокированы флагом.

Код: [src/lib/estimates.ts](../src/lib/estimates.ts), [src/lib/security.ts](../src/lib/security.ts), [архитектура](architecture.md).

## 4. Что сломается при росте пользователей

1. **Список смет** читает все сметы мастерской за один запрос. Тяжёлые данные (позиции, события, тексты) я уже убрал: выбираются только поля для статуса. Следующий шаг — серверная пагинация и фильтры.
2. **Лимиты запросов** хранятся в таблице PostgreSQL. Нужна периодическая очистка, а при большой нагрузке — перенос в Redis или на прокси.
3. **Соединения с БД:** при нескольких инстансах нужен пул (PgBouncer).
4. **AI:** у внешнего провайдера свои квоты. Нужны очередь, повторы, платная модель после согласования бюджета и мониторинг доли ошибок.
5. **Нет мониторинга и нагрузочного теста:** прежде чем заявлять пропускную способность, нужно его провести.

## 5. Первый клиент и почему он заплатит

Первый кандидат — [FixUp](https://fixup.uz/), ремонт ноутбуков в Ташкенте: на сайте прямо указано, что цена согласуется до ремонта, а общение идёт в Telegram. Значит, процесс, который автоматизирует продукт, у них уже есть.

За что платить: меньше споров «я на это не соглашался», у клиента профессиональная смета вместо голосового, история версий и решений. Модель продаж: бесплатный двухнедельный пилот, затем 199 000 сум в месяц. Это гипотеза, которую проверит пилот. Текст обращения и план есть в [first-sales.md](first-sales.md).

## 6. Что улучшу за 3 дня

1. **День 1 — пользователи.** Показать продукт 3–5 мастерским, посмотреть, как они сами создают смету, записать, где застревают.
2. **День 2 — доступ и надёжность.** Восстановление пароля по email, серверная пагинация, стабильная AI-модель после согласования бюджета.
3. **День 3 — публичный пилот.** HTTPS-хостинг с постоянной БД и внешними бэкапами, мониторинг ошибок, отправка ссылки кнопкой в Telegram.

Порядок такой, потому что главный риск не технический: нужно подтвердить, что мастера готовы этим пользоваться.

## Дополнительно: почему версии неизменны

Клиент соглашается на конкретные работы и цену. Если тихо править опубликованную смету, согласие теряет смысл. Поэтому правка создаёт новый черновик, а публикация заменяет версию; старые условия и решение остаются в истории.

## Небольшая правка по запросу

Порядок действий: найти компонент или сервис через поиск, объяснить последствия, внести правку, запустить `npm run typecheck`, `npm run lint` и нужный тест, показать результат в браузере. Где что лежит:
- тексты интерфейса — [src/components](../src/components), статусы и форматы — [src/lib/locale.ts](../src/lib/locale.ts);
- правила денег и версий — [src/lib/estimates.ts](../src/lib/estimates.ts), [src/lib/validation.ts](../src/lib/validation.ts) (после правки запустить `npm run test:integration`);
- API — [src/app/api/service/[...path]/route.ts](../src/app/api/service/[...path]/route.ts).
